# Planner Layer

The **Task Planner** box of the CyberDog architecture, minus the Intent
Parser (that's `cyberdog/language/`). It turns a destination into a
route across floors and, at each checkpoint, into a pixel target VAMOS can
steer toward:

```
target "physics lab" (+ optional floor)      from cyberdog/language/
        │
        ▼ building_router.py
pick the right copy of the place (requested floor / same floor / nearest floor)
A* on each floor's grid, split at the lift
        │  legs: [(floor 1, Route), (floor 3, Route)]
        ▼ checkpoint_projector.py
carrot point 2-4 m ahead → camera pixel (u, v) → PaliGemma <loc> tokens
        │
        ▼
"Navigate to x=<loc0511>, y=<loc0612>."   or   [ALIGN] turn left   or   [ARRIVED]
```

Everything here runs **without hardware or ROS**: the robot pose, camera and
building are simulated. `main_planner.py` in the project root runs the whole
pipeline (command → model → this layer).

## Files

| File | What it is |
|---|---|
| `building_router.py` | Loads the building (per-floor grids + `locations.json`), resolves place names, plans multi-floor routes |
| `checkpoint_projector.py` | Carrot-point selection + pinhole projection to a pixel; self-test when run directly |
| `camera_config.yaml` | Camera intrinsics — **placeholder values** until the real camera is known |
| `test_locations.py` | Checks the building matches the model's training locations (optionally runs the model too) |
| `visualize_route.py` | Draws a planned trip on the floor maps (PNG) to check routes by eye |

Data it reads (generated, lives in `data/`):

- `data/building/locations.json` — place name → list of `{floor, xy, door_xy}`
- `data/building/maps/floorN/room_map.{png,yaml}` — occupancy grid per floor
- `config/map_config.yaml` — A* settings (checkpoint spacing, turn threshold)

## The building (placeholder)

Generated by `scripts/mapping/generate_building.py`. `NUM_FLOORS` and
`ROOMS_PER_FLOOR` are imported from `cyberdog/language/generate_dataset.py`,
so the map and the model can't disagree about how many rooms exist.

Every floor is the same 48 × 19 m shell: a 3 m corridor along the middle,
8 rooms on each side, a doorway from each room to the corridor, a lift at the
east end and a stairwell at the west one. Numbered rooms take the 5 west-most slots on each side
(`x01`-`x05` south, `x06`-`x10` north). Named places use the east slots,
pinned in `NAMED_ROOMS`:

| library | 1, 2 | north 7 — same spot, one two-storey library |
| office | 1 | south 6 |
| main entrance | 1 | south 7 (robot start) |
| cafeteria | 1 | north 5 |
| computer engineering lab | 2 | south 6 |

## `building_router.py`

```python
router = BuildingRouter()
router.floors                       # [1, 2, 3]
router.floors_of("library")         # [1, 2]
target = router.resolve("restroom", current_floor=1, current_xy=(45, 4), floor=2)
legs = router.plan(start_floor=1, start_xy=(45, 4), target=target)   # [(1, Route), (2, Route)] or None
```

- **`resolve`**: with `floor` given, only that floor's copy (or `None` if the
  place isn't there). Without it, same floor first, then the closest floor,
  then the closest by distance.
- **`plan`**: same floor → one A* call. Different floor → A* to the lift,
  then lift → target on the target floor. The last checkpoint of the first
  leg announces "Take the lift to floor N"; every route ends with
  "Destination reached".
- **`transit`**: the lift serving both floors, or `NoAccessibleRoute` if none
  does. It does not fall back on the stairs, because there is nothing to fall
  back to: leading a blind user to a stair head is worse than saying "I cannot
  get you to floor 3 from here".

**Stairs are never routed through.** The user cannot see the steps and has one
hand on the handle, so the stairwells are `stairs` zones in
`data/building/zones.json` — full stop, announce — and
`_block_zones()` stamps them into the *planning* grids as obstacles before any
A* call (`self.grids` stays raw for drawing and tests). `resolve()` refuses
them as a destination: `resolve()` raises `NoAccessibleRoute` rather than
routing there and halting on arrival.

Asking for the stairs is still a fair thing to ask, though -- you might be
meeting someone there. So the callers do not refuse to move: `approach()`
walks the dog to the nearest safe spot outside the zone, a metre clear of the
edge (`APPROACH_CLEARANCE`), and the arrival announcement becomes "I can take
you to the corridor by the stairs, but no closer". `nearest_free()` spreads
over the raw grid rather than in straight lines, so the point it finds is the
corridor outside the stairwell and not the room on the other side of the wall.

The zone stops at x=2.5, half a metre short of the doors of the westernmost
rooms, so sealing the stairwell does not also take rooms 101 and 106 off the
map; `sim/scene/stairs.py` sizes the flights to match.

## `checkpoint_projector.py`

Uses the same pinhole math as VAMOS's
`vamos_ws/src/vamos/nodes/navigate.py:project_point_to_image`, but takes the
pose as an argument instead of reading ROS tf, and projects a point *ahead
on the route* instead of the final goal.

1. **`pick_carrot`** — first checkpoint 2-4 m from the robot; if the route
   jumps past 4 m, the point on that segment at exactly 4 m.
2. **`project_to_pixel`** — map → robot frame (rotate by yaw) → camera frame
   (OpenCV: z forward, x right, y down; goal on the floor `camera_height`
   below the lens) → `u = fx·x/z + cx`, `v = fy·y/z + cy`.
   - Visible and inside `fov_margin` → `TRACK` with pixel + `<loc>` tokens (1024 bins, `int(u / width · 1024)` capped at 1023 — the same scale VAMOS decodes with)
   - Behind the camera or outside the margin → `ALIGN` with `turn: left/right`
3. **`project_route`** — both steps; `ARRIVED` when no waypoints remain.
4. **`vamos_prompt`** — `"Navigate to x=<locXXXX>, y=<locYYYY>."`

### Camera config

`camera_config.yaml`: `width`, `height`, `fx`, `fy`, `cx`, `cy`,
`camera_height` (m), `fov_margin` (px). All placeholders. With the real
camera on ROS: `rostopic echo /<camera>/camera_info` — `K` is
`[fx, 0, cx, 0, fy, cy, 0, 0, 1]`; measure `camera_height` with a tape.

## Running it

Planner-only pieces need `numpy pyyaml pillow scipy` (the `cyberdog_map`
conda env during development). The full pipeline and `--with-model` also
need the model libraries (the `vamos_mac` env).

```bash
# Projector self-test (7 checks)
python -m cyberdog.planning.checkpoint_projector

# Building vs. training set: every location exists, is free space, and is reachable
python tests/test_locations.py
python tests/test_locations.py --with-model   # + one command per location through the model

# Whole pipeline, from the project root
export KMP_DUPLICATE_LIB_OK=TRUE
python -m cyberdog.main_planner "I need to pee upstairs, then the library and the caf"
```

### Checking routes by eye

The printed output can't show a route cutting through a wall, so draw it:

```bash
python -m cyberdog.planning.visualize_route "physics lab"                 # place names
python -m cyberdog.planning.visualize_route "restroom@2" library cafeteria # name@floor, multi-stop
python -m cyberdog.planning.visualize_route --command "I need to pee upstairs, then the caf"  # via model
```

Saves `output/route_images/<stops>.png` (or `--out`): one panel per
floor visited, room labels, each stop's route in its own color, checkpoints
with announcements, START square and numbered stop stars. A correct route
stays in the corridor, enters rooms through door gaps, uses the lift (east
end) to change floor, and ends inside the right room. If a drawn route ever
touches the stairwell at the west end, something in the Behavior Layer wiring
has come undone.

This is how a real bug was found: the grids were built from ~1M surface
samples, so walls came out as hollow dotted outlines and A* walked *inside*
them. Grids are now built with `--points 4000000 --inflate 0.25` (see below),
which fills the walls and keeps routes 0.25 m from them.

Reading `main_planner.py` output:

- `Split into N stops` — from `command_splitter.py`
- `Floor phrase found: floor N` — from `floor_parser.py`
- `Route: A (floor x) -> B (floor y)` — each stop starts where the previous ended
- `Step k: Navigate to x=<loc…>, y=<loc…>.` — carrot visible, VAMOS prompt
- `[ALIGN] turn left/right` — rotate first; `[ARRIVED]` — end of a leg
- Errors (and the run stops) for an unknown place, a nonexistent floor, or a
  place that isn't on the requested floor

Rebuilding the building after editing `NAMED_ROOMS` (needs `open3d opencv-python`
for the second step, `cyberdog_map` env):

```bash
python scripts/mapping/generate_building.py
# only needed if walls/room sizes changed:
for n in 1 2 3; do
  python scripts/mapping/mesh_to_grid.py --mesh data/building/floor$n.obj \
      --output data/building/maps/floor$n --up-axis z --points 4000000 --inflate 0.25
done
python tests/test_locations.py
```

### Linux

Same commands; paths are resolved relative to each file, so they work from
any directory.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install numpy pyyaml pillow scipy matplotlib   # matplotlib: visualize_route.py
# full pipeline / --with-model:
pip install torch transformers peft trl datasets accelerate
```

`KMP_DUPLICATE_LIB_OK` is a macOS-only fix and harmless on Linux.

### macOS import-order gotcha

Importing the map stack (numpy/PIL) **before** torch crashes with
`OMP: Error #179`. `main_planner.py` and `test_locations.py` load the model
first on purpose — keep that order if you write another entry point.

## Known limitations

- **Simulated pose.** The demo places the robot on each checkpoint facing the
  next one, so the carrot is almost always dead ahead and most prompts are
  the same `<loc0511>, <loc0612>`. Real prompts vary once the pose comes
  from localization (FAST-LIO).
- **Level camera assumed** — no tilt. Add a pitch rotation in
  `project_to_pixel` once the real mount is known.
- **Placeholder building and camera values** (see above).
- **Wall clearance is baked into the grid** (`--inflate 0.25`). The router
  only adds `robot_radius - grid_inflation` on top (both in
  `map_config.yaml`, currently 0), so the clearance is not applied twice.
  Doorways are 1.2 m, so total inflation above ~0.5 m closes them.
- **Stairs are a single point per floor**; no elevator, no stair traversal
  time/cost, no "press to confirm" handling yet.
- **No state machine yet.** The diagram's deterministic FSM
  (IDLE → GLOBAL_NAV → ALIGN → TRACK → ARRIVED) is only printed, not run as
  a loop that rotates on ALIGN and re-projects.
- **Visual QA isn't answered.** A stop with a question is navigated to and
  the question is printed as unanswered.
- **Fallback PaliGemma goal adapter** (for places not in the map) isn't built;
  unknown places are an error.
